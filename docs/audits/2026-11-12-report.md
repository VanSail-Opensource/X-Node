## Review and verification method

The review traced admission, credentials, mutable configuration, native runtime ownership, traffic accounting, utility receipts, financial credit, crash recovery, update/rollback, privileged host operations and release provenance across their callers and persistence boundaries. Searches and static analysis supported the full-file reads; they did not substitute for reading the code.

Confirmed behavior changes received focused regression coverage. Where practical, baseline source overlays or old binaries reproduced the failure before the fixed implementation was checked. Assertions target recovery boundaries, ownership, replay behavior and observable outcomes. Existing compatibility evidence was retained even when the corresponding behavior is retired.

Local checks used temporary directories, fake host runners and socket-free tests. The workspace does not permit live socket fixtures. No production host, real installer, privileged firewall takeover, production signing key or live customer credential was exercised locally. Disposable Debian virtual machines and the complete real-kernel suite ran in hosted CI.

## Findings and completed changes

Severity expresses the practical impact of the demonstrated failure in its supported execution path. It does not imply an unauthenticated internet exploit or a confirmed production incident.

### XN-01 — Medium: terminal job refusals could become ambiguous after restart

Provably terminal refusals lacked private durable evidence distinguishing them from mutations whose outcome was uncertain. Recovery could therefore lose the exact refusal semantics. The job journal now preserves private terminal-failure evidence, bounds its encoded size with the rest of the receipt, and keeps ambiguous legacy mutations conservative. Wire response schemas are unchanged. Evidence: `internal/agent/job_terminal_failure_test.go`, existing restart/refusal/recovery tests, and the job journal/bounds implementation.

### XN-02 — Medium: scheduled DDNS work reused receipt identifiers

Repeated scheduled executions could collide with previous job receipts and suppress fresh work. Scheduled DDNS jobs now have distinct receipt IDs; maintenance clocks advance only after worker admission. Evidence: `internal/agent/utilities_schedule_test.go` and `utilities.go`.

### XN-03 — High: principal replacement could escape an accounting flush barrier

A handler can retain an immutable counter owner while its current authentication identity changes. Flushes scoped only to one interpretation could miss an in-flight handler during period closure. The session registry now preserves original accounting identity and checks both original and current owners for principal/period barriers. Regressions cover old and replacement principals in both directions. Evidence: `internal/sessions/accounting_identity_barrier_test.go`, `accounting.go`, `period_barrier.go`. This is a protocol/rekey barrier risk; no active panel operation was found that rewrites a period owner during closure.

### XN-04 — Medium: recovery reads lacked an early bounded regular-file boundary

Malformed or substituted state files could allocate excessively; opening a FIFO before checking its type could block startup. Recovery now uses bounded, nonblocking, no-follow regular-file reads and checks descriptor identity. Oversize, special-file, symlink and FIFO cases are rejected before state is accepted. Evidence: `internal/state/recovery_file.go` and `recovery_bounds_test.go`.

### XN-05 — Medium: atomic-write durability errors were hidden

A successful rename was reported as fully durable even when syncing the parent directory failed. Atomic writes now propagate directory-sync errors so callers retain an honest recovery boundary. The final XN-15 follow-up additionally exposes `AtomicWritePublished`, which reports whether rename occurred independently of the durability error. The existing authorization store still publishes a fresh in-memory authorization view only on full success. Evidence: `internal/state/store.go`, `internal/state/atomic_publication_test.go` and the existing recovery/write regressions.

### XN-06 — Medium: transit secrets were missing from shared redaction

Authenticated transit credentials were not registered with the common log redactor. They now join the existing secret set before errors can cross the logging boundary. Evidence: `internal/agent/transit_redaction_test.go` and `synchronization.go`.

### XN-07 — High: the selected Go toolchain contained a reachable HTTP vulnerability

The comparison vulnerability scan identified reachable GO-2026-6859 / CVE-2026-97054 with Go 1.27.3. The module now requires Go 1.27.4, and the Linux validation bootstrap uses that release with its official digest. The Go 1.27.4 scan reports no called or imported vulnerabilities. Its module-only report for unimported `x/crypto/openpgp` was distinguished from reachable code. Evidence: `go.mod`, `docs/dependency-security.md`, `scripts/linux-check.sh`, hosted vulnerability scan.

### XN-08 — Low: an unused certificate lifecycle obscured the live pool contract

Unused direct certificate reconfiguration/fingerprint paths were removed. The production pool remains keyed by complete immutable profile configuration. Tests now cover challenge port, propagation delay and startup timeout as identity inputs. Evidence: `internal/cert/acme_lifecycle.go`, `cert.go`, `cert_test.go`.

### XN-09 — High: updates and rollback did not consistently fence hourly formats

Replacing a binary without the required hourly formats could strand cached authorization or retained financial credit obligations. Update and rollback checks now inspect persisted formats without recovering live obligations or rewriting their bytes, retain the fence after ACK compaction, and preserve the pristine-journal upgrade path. Compiled binary capabilities are distinct from health-gated operational negotiation. Evidence: `internal/update/hourly_compatibility_test.go`, `internal/hourly/credit_compatibility_test.go`, `internal/agent/binary_capabilities_test.go`.

### XN-10 — High: accepted XHTTP download settings could fail at dialer use

The native builder accepted combinations the effective dialer could not safely use, including missing address or incompatible transport cases. Early validation now rejects them before listener mutation. Evidence: `internal/protocol/native_xhttp_download_test.go`, builder-backed protocol regressions, and the live listener-preservation test in `internal/kernel/xray/xhttp_validation_test.go`.

### XN-11 — Medium: nested member transports bypassed outer endpoint checks

Effective nested XHTTP download transports, native field case aliases and special-purpose destinations were not all covered by the member endpoint/owned-peer guard. Validation now follows the native interpretation and applies the same restrictions to nested transports and relevant socket/file settings. Evidence: `internal/protocol/member_transport.go` and `member_transport_test.go`. The panel's direct DIY path already had endpoint restrictions; the finding does not claim a demonstrated public panel exploit.

### XN-12 — Low: two uncalled helpers retained retired behavior

The unused protocol URL helper and host distribution check were removed after caller review. Supported platform detection remains capability-based for apt/systemd hosts. Legacy wire/recovery evidence was retained. Evidence: `internal/protocol/types.go`, `internal/host/commands.go` and module documentation.

### XN-13 — Medium: malformed recovery journals could reach destructive decisions

Updater and firewall recovery observers accepted incomplete, null or ambiguous compatibility policies before cleanup, mutation or migration. They now share a bounded regular-file reader and reject invalid recovery evidence before those actions. Evidence: `internal/update/transaction_read_test.go`, `compatibility_recovery_test.go`, `firewall_compatibility_test.go` and `internal/firewall/recovery_integrity_test.go`.

### XN-14 — High: the first firewall completion marker preceded complete recovery material

An interruption after the native snapshot marker but before original iptables tables/manifest became durable could make a retry omit uninstall recovery evidence. Publication now follows durable original tables and their manifest. Evidence: `internal/firewall/boot.go` and recovery-integrity tests with fake host runners.

### XN-15 — High: post-publication failure restored an obsolete source epoch

After a source checkpoint was committed, cleanup failure could leave memory referring to the previous journal epoch. Later successful journal appends would use the obsolete epoch and be skipped on restart, losing acknowledged bans, exemptions or events. The checkpoint epoch must remain authoritative once rename publishes it, including when a later durability or cleanup step fails.

The initial fix and regression at `49225410` covered failure while removing the obsolete journal. Final review of `5dc1fe8a` identified the earlier boundary: rename can succeed and the subsequent directory sync can fail before the old writer updates its in-memory epoch. The follow-up now reports rename visibility separately from durability and advances `haveSnapshot`/`JournalEpoch` at that boundary. Both source-update and ordinary snapshot rollback guards use the updated epoch.

Every later journal append already syncs its file and the shared directory before applying or acknowledging the record. A successful append therefore completes any uncertain checkpoint directory barrier. Failed writes continue to report failure; rename visibility is not presented as a durability guarantee. Per-instance failure injection avoids a mutable global test hook.

Evidence: `internal/state/store.go`, `internal/state/atomic_publication_test.go`, `internal/firewall/ban_persistence.go`, `internal/firewall/ban_writes.go`, `internal/firewall/source_sync.go` and `internal/firewall/source_recovery_test.go`. Regressions cover real rename followed by an injected directory-sync failure, failed rename preserving existing data, and source-sync failure followed by a successful append and restart retaining both earlier and later receipts. The follow-up was authored and fully reviewed while the workspace was unavailable; its automated validation is supplied by the final hosted checks.

### XN-16 — High: the legacy source upgrade did not activate its rollback fence

Streaming older inline firewall sources into the newer disk format failed to activate the existing compatibility fence. The upgrade now records the format boundary so an incompatible binary cannot be selected afterward. Evidence: `internal/firewall/source_upgrade.go` and legacy-upgrade regressions.

### XN-17 — Medium: compressed checkpoints had incomplete integrity and size checks

Missing identity, duplicate records and trailing gzip data were not consistently rejected under one bounded decompression budget. The decoder now validates the full checkpoint without an unbounded trailing drain. Evidence: `internal/firewall/ban_decode.go`, `ban_recovery_integrity_test.go` and `ban_bounds_test.go`.

### XN-18 — Medium: unreadable retention references could authorize deletion

Source cleanup could infer that files were unreferenced when recovery metadata was unreadable. It now defers deletion until references can be interpreted safely. Ownership checks also preserve unrelated caller/operator files and external symlink targets. Evidence: `internal/firewall/source_cleanup.go` and `retention_integrity_test.go`.

### XN-19 — Medium: a newly created ban journal lacked directory-entry durability

The first append could be acknowledged before the containing directory entry was synced. Creation now establishes that durability boundary before receipt publication. Evidence: `internal/firewall/ban_journal.go` and journal/recovery regressions.

### XN-20 — Medium: immediate grants and expiry events bypassed existing capacity limits

The 100,000 exemption limit and 4096 pending-event limit were not consistently applied to immediate grants and expiry reporting. The same bounds now cover those paths. Paid/manual grants and absolute expiration times remain intact while acknowledgment capacity is exhausted. Evidence: `internal/firewall/exemption_capacity.go`, `ban_bounds_test.go`, and the exemption/expiry tests. The existing grant limit was enforced; no paid benefit was silently truncated.

### XN-21 — Low: retired ban-extension state and an unused source wrapper remained

Unconsumed local extension fields and unreachable compatibility branches were removed after caller/state-format review. Historical wire and recovery evidence remains available. Evidence: firewall ban state/sync/update/source implementation and module documentation.

### XN-22 — Medium: nested dialer dependencies escaped graph and reload decisions

Dependency validation and reload reconstruction did not consistently include effective nested XHTTP dialers, native field case aliases, extra replacement semantics or penetrating sockets. The dependency graph now follows the pinned builder, rejects missing/cyclic peers and reconstructs affected mux paths. Evidence: `internal/protocol/native_dependencies.go`, `internal/kernel/xray/outbound_dependencies_test.go` and outbound validation/reload code.

### XN-23 — High: isolated native clients skipped early policy validation

Speed-test and asset-download clients could reach file reads or native construction without the early XHTTP/policy guard used by the main runtime. Prepared clients now validate before those operations. Evidence: `internal/kernel/xray/client_prepared.go`, protocol and isolated-client regressions. This concerns the supported native-client construction boundary; production traffic was not exercised during reproduction.

### XN-24 — Low: an unconsumed configuration hash and inert helper added dead work

The unused prepared base hash, its extra configuration clone/hash work and an inert Shadowsocks helper were removed. Effective runtime identity and rebuild decisions remain covered by their specific dependency tests. Evidence: `internal/kernel/xray/config.go`, `identity.go`, `inbound_render.go`.

### XN-25 — Medium: malformed geodata pointers could delete serving assets

Invalid active/previous generation pointers could be interpreted as absent references during cleanup, risking serving or rollback assets. Pointer recovery is now strict and bounded, malformed references block destructive cleanup, the historical flat-directory sentinel is preserved, and staged directories are synced before verified publication. Twenty destructive-pointer cases were reproduced against the previous implementation. Evidence: `internal/geodata/generation_pointer.go`, `recovery_test.go`, `cleanup.go`, `generation.go`.

### XN-26 — Medium: non-finite arithmetic weakened remote result verification

Finite inputs could overflow expected arithmetic to infinity, making a fabricated finite result pass an unbounded tolerance comparison. Validation now rejects non-finite expectations, revalidates the original batch, and uses an incremental mean for large nonnegative forecasts. Evidence: `pkg/compute/numeric_integrity_test.go`, `execute.go`, `validate_model.go`, `validate_result.go`. A billing exploit is not inferred solely from this numerical defect; panel request/result bindings are reviewed separately.

### XN-27 — Medium: signing-key output paths could overwrite key material

Equal paths, symlink aliases or concurrent creation could overwrite existing private/public key output. Generation now requires distinct absent paths and exclusive durable writes. Regressions cover preservation, competing writers and private/public correspondence; the old CLI reproduced private-key loss for equal output paths. Evidence: `cmd/release-sign/keygen.go`, `keygen_test.go`.

### XN-28 — Medium: public documentation promised retired recovery and DNS behavior

The API reference still described restart-durable new traffic, host DNS redirection, SmartDNS lifecycle and five-second reports. It now documents volatile boot-stream traffic, durable master receipts before ACK, separate hourly credit obligations, sampled versus total connection observations, current report cadence, bounded job receipts and activation completion. Historical release notes remain intact. Tooling references were aligned with the supported Go version and pinned native integration; a retired personal module-cache path was removed. Evidence: `docs-site/reference.json`, protocol/recovery/hourly/job documentation and `scripts/linux-check.sh`.

### XN-29 — Low: resizing documentation could leave a hidden sidebar focusable

When a desktop layout changed to mobile, the closed sidebar's inert state was not always updated. The resize path now applies the same visibility/focus boundary as explicit navigation changes. Evidence: `docs-site/app.js`. JavaScript syntax and static documentation generation passed; no browser interaction test is claimed.

## Retained architecture and governance boundaries

### Volatile new traffic can be lost on agent failure

New boot-stream traffic intentionally resides in memory until committed by the master. A crash can lose unreported bytes, which can underbill usage or increase a refund calculated from observed usage. Legacy durable traffic replay and durable hourly byte-credit obligations are separate mechanisms. The audit corrects the documentation and barrier ownership; it does not silently replace the accepted traffic-loss policy with a new financial architecture.

A product promising lossless metering or exact post-crash refunds requires an explicit change to this policy, persistence design, capacity limits and recovery protocol. The panel's refund/settlement and hourly credit paths require their own owner/generation checks; they are covered by the companion panel audit.

### Agent capability and binary identity are trust assertions

The authenticated agent reports its capabilities and binary identity. These are useful compatibility/provenance inputs, not hardware-backed remote attestation. A compromised authorized host remains within the operator trust boundary. No claim of protection against an actively malicious enrolled root host is made.

### Repository administrator bypass remains intentional

The existing `enforce_admins=false` governance choice was preserved. Required release provenance still binds the tested canonical main commit. The audit did not alter repository ownership or administrative authority.

### Additional required checks conservatively block release

The provenance gate recognizes the exact supported six-check evidence set. Repository administrators may preserve or add other required checks, but extra checks block release until the gate explicitly supports their provenance. The fix documents this boundary; it does not weaken verification to accept an arbitrary subset.

### Retirement preserves immutable evidence

Unused executable branches and helpers were removed only where caller/state-contract review showed they were inactive. No tracked file was deleted. Legacy compatibility tests, historical release notes, accounting evidence and supported recovery formats were retained. Age or a legacy name alone was not treated as a reason to delete a file.

## Limits and follow-up discipline

All tracked files in the stated snapshots are covered; this is not a proof that every possible runtime defect is absent. The review does not include manual inspection of every downloaded transitive dependency, real production data, external provider implementation, operating-system kernel implementation or production deployment configuration.

Potential concerns without a demonstrated supported failure were not labeled fixed or turned into broad speculative rewrites. Future changes to credential lifecycles, journal formats, accepted traffic loss, branch protection or master-agent protocol must preserve the documented ownership and durability boundaries and add targeted regressions.

The panel integration audit is separately scoped. Its remaining work does not change the completed X-Node file coverage, and this report does not imply that the panel or its database modules have already received complete coverage.
